# Fixed Parallel Runtime and Coremod Architecture

> **Applies to:** Minecraft 1.20.1, Forge 47.4.20, GTCEu 26.7.3, GTOCore 0.5.6-beta, GTOLib 26.7.4, GTOHJS 2.1-alpha fix1.

## 1. UI Parallelism Is Not Runtime Recipe Parallelism

The parallel trait on `NoEnergyCustomParallelMultiblockMachine` only stores, synchronizes, and displays the player's configuration and exposes it through `getParallel()`. It does not modify `GTRecipe` automatically. A no-energy controller must call this explicitly in `getRealRecipe(...)`:

```java
GTRecipe modified = ParallelLogic.accurateParallel(this, unit, recipe, getParallel());
if (modified != null) {
    modified.duration = 1;
}
return modified;
```

The Hyperdimensional Forge previously set both its minimum and maximum to `524288`, so the left-side UI correctly displayed fixed parallelism while the running recipe still had `parallels == 1`. Fix1 follows GTOCore's `AdvancedPrimitiveBlastFurnaceMachine` and uses the real execution path above. Do not merely write `recipe.parallels = 524288` or copy item quantities manually; `accurateParallel` creates a consistent parallel recipe from recipe contents, available inputs, and output capacity.

The `ONE_TICK` definition modifier in `HyperdimensionalForgeRegistration` locks duration only; it does not provide parallelism. The runtime controller sets final duration to one tick again in `getRealRecipe(...)`, ensuring that the parallel-expanded recipe also follows the one-tick contract.

## 2. Different Contract for Steam Controllers

The Hyperdimensional Steam Furnace extends GTOCore `BaseSteamMultiblockMachine`. That parent already performs the following work in `getRealRecipe(...)`:

1. Check that recipe voltage does not exceed the machine's steam voltage.
2. Call `ParallelLogic.accurateParallel(..., maxParallels)`.
3. Apply duration scaling and available steam overclocking.
4. Return the actual parallel recipe.

The child must therefore continue calling `super.getRealRecipe(...)` and must not invoke `accurateParallel` a second time, which would scale inputs and outputs twice. `524288` is a ceiling rather than an unconditional value; available inputs and output capacity still limit actual parallelism. Validation must use ME input/output hatches large enough for the test amount, provide N input sets, and confirm `parallels == N` in the running recipe. A left-side configuration label, one input set, or a normal bus too small for outputs cannot prove a parallelism failure.

## 3. Freely Fillable Internal Structure Positions

The Advanced Alchemy Cauldron maps its fourteen hollow positions with:

```java
.where(' ', Predicates.any())
```

When GTCEu's `FactoryBlockPattern.where` sees `isAny()`, it omits that symbol from the structure predicate. Those positions may therefore contain air, fluid, or arbitrary blocks; placement and removal do not trigger structure rechecks, and hatches at those positions do not attach to the controller. The resource pattern and fourteen-character count assertion remain unchanged.

Use `Predicates.air()` only when air is mandatory. Do not replace `Predicates.any()` with an ordinary custom always-true predicate because it may still enter structure listeners and part collection.

## 4. Current Code Responsibility Boundaries

| Layer | Responsibility | Maintenance rule |
| --- | --- | --- |
| `META-INF/coremods.json` + coremod JS | Insert minimal calls or builder bytecode into GTO static initialization and native recipe windows | Keep thin; validate target method, descriptor, and match count |
| `bootstrap/*.java` | Register machines, recipe types, and items; validate final state | Reuse verified registration templates for new features |
| `machine/*.java` | Recipe runtime, parallelism, threads, hatches, and persistent state | Keep runtime behavior in Java rather than JS |
| Mixin | Handle only verified instance behavior unreachable through ordinary registration windows | Do not duplicate a contract already modified by the coremod |
| resources | Patterns, languages, models, textures, and metadata | Keep IDs aligned with Java definitions |

Forge 1.20.1 loads the Nashorn coremod JavaScript referenced directly by `META-INF/coremods.json`. Mechanically changing that target to `.java` or `.kt` is not recognized by Forge. A complete migration would require implementing and registering a ModLauncher transformation service and would change loading order, class-loading boundaries, and release surface, creating far more risk than benefit. The current optimization strategy is to retain a thin JS injection layer and keep registration state, validation, and runtime behavior in Java. This task removes one fully duplicated `appendRecipePowerAndDuration` definition from the coremod without changing generated bytecode.

## 5. Documentation-First Maintenance Workflow

Future development begins with `docs/README_ZH_EN.md`, the document for the target feature, and `GTOHJS_REGISTRATION_TEMPLATES_ZH.md`. The following changes can use documentation and existing successful templates directly:

- adjusting machine parameters, tooltips, recipe quantities, or known structure predicates under the same dependency versions;
- reusing an existing registration window, controller parent, or recipe-building entry point;
- fixing a documented common error when verification matches the document.

Re-audit GTOCore, GTOLib, or GTCEu source only when:

- documentation does not cover the target behavior or conflicts with active source;
- a dependency version, method descriptor, field type, or registration stage changes;
- a new core runtime mechanism, coremod/Mixin target, or previously unused hatch is introduced;
- implementation from the documentation fails compilation, startup, or in-game behavior verification.

During a re-audit, read only the relevant classes and direct call chain, then write the conclusion, applicable version, template, and verification boundary back to documentation. When documented behavior changes, update source and the corresponding English documentation in the same task.

## 6. Minimum Verification

1. Run `node --check src/main/resources/coremods/gtohjs_machine_registration.js`.
2. Run a Java 21 incremental build; coremod injection match counts and registration validation must pass.
3. After the fixed client starts, confirm GTOHJS has no `ERROR/FATAL` and the affected machine patterns build successfully.
4. For the Forge, use hatches that can hold N input/output sets and verify actual input consumption and output production are both N at a duration of one tick.
5. Verify the Steam Furnace parent parallel path in the same way; do not misdiagnose an I/O limit as fixed parallelism of one.
6. Place and remove ordinary blocks in all fourteen Cauldron interior positions. The machine must remain formed and those blocks must not contribute hatch abilities.
